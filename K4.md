# Kunundrum — K4 board code (specification and implementation plan)

**Status (2026-11-24): fully implemented; K3 removed (app 4.0.1, solver v0.21).** Remaining manual step: rebuild the WASM bundle (`node Solver/wasm/build.js`, needs Emscripten). Facts marked *(catalog check)* were verified against all 300 levels on 2026-11-23.

## 1. Goals

- A **short, text-only, alphanumeric, lossless** board code: about 45 characters on average including balls (K3 board data without title/solution averages about 133, tunnels and switch mappings included).
- **One canonical string per board** (the solver and the editor emit it; the decoder rejects anything else).
- Natural output format for a future random board generator (walls first; see the project notes), but K4 is a general board code, not generator-specific.

## 2. Validation limits that come with K4 (`Core.validateBoard`, RULES.md §6)

K4 is only lossless under these rules, so they become part of board validation for **every** entry path (editor, import, share links, solver):

1. **Board size 1–15 × 1–15** (was 1–32). With w+h ≤ 30 every perimeter index fits in one character.
2. **Hex values** are exactly one of `-20, -15, -10, -5, 5, 10, 15, 20` (was any nonzero integer in ±10000) *(catalog check: all 56 hexes comply; the editor's value field becomes a selector of these 8)*.
3. **Balls: 1–61** (was 1–128; catalog maximum 9).
4. **A wall cell carries at most one tunnel opening** (it is the wall side of at most one opening) *(catalog check: 0 violations)*. Two openings on the same *floor* cell, or openings on the board edge at a corner, stay legal.
5. **Switch control lists are identical or disjoint** (RULES.md §3 says "expected"; make it required) *(catalog check: no violations)*; every switch controls at least one element *(checked)*; every gate is controlled by some switch *(checked: 410/410)*; every inactive teleport is controlled *(checked: no uncontrolled inactive teleports)*.
6. At most 31 tunnel pairs and at most 61 switch groups (far above anything real: catalog maximum 7 pairs, 7 groups).

Update RULES.md §6 (limits) and the editor so that boards violating these cannot be created. Everything else in RULES.md is unchanged.

## 3. Format

`K4.` followed by an **alphanumeric payload** (case-sensitive; no punctuation, no padding, no separators). The payload is a fixed sequence of sections: **header · grid · edge openings · tunnel pairing · switch mapping · balls**. Every section's length is determined by what has been read before it, so no delimiters are needed.

**Number characters (N62).** Wherever a section stores a number in one character, it uses `0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ` with value 0–61 in that order. (The grid uses its own symbols, below.)

**Cell order.** Index `i = (x-1) + (y-1)*w`, the project's lexicographic order (left to right, then bottom to top; RULES.md §1). All "cell order" and "ascending" statements below refer to it.

### 3.1 Header (3 characters)

`N62[width]`, `N62[height]`, `N62[wallColor]` with wall colour 0 = blue (also when omitted in the JSON), 1 = red, 2 = green.

### 3.2 Grid

Read tokens from cell 0 until all `w*h` cells are covered:

- **Digits** = a run of floor cells with no feature. The run length is the decimal number (no leading zero, at least 1). Runs are always **maximal**, so two floor runs are never adjacent and a multi-digit number is unambiguous.
- **Letters** = one cell each (except wall runs), assigned consecutively from `abc…xyzABC…Z` in this order:

| Letters | Meaning |
| --- | --- |
| `a`–`f` | run of 1–6 wall cells |
| `g h i j` | wall cell that carries the gap of a tunnel opening with side `u`, `d`, `l`, `r` (the opening's floor cell is the neighbour on the opposite side: `g` = floor cell below this wall cell has an opening with side `u`) |
| `k l m n` | fixed arrow `u d l r` |
| `o p q r` | goal `R G B Y` |
| `s t` | gate inactive, active |
| `u` | switch |
| `v w x y z A B C D E` | teleport: colour R, G, B, Y, `*` in this order, each as (active, inactive): `v`=R active, `w`=R inactive, `x`=G active, … `D`=`*` active, `E`=`*` inactive |
| `F G H I` / `J K L M` / `N O P Q` | rotating arrow, type clockwise / counterclockwise / flip, each with direction `u d l r` as displayed at clock phase 0 (as in the board JSON) |
| `R S T U V W X Y` | hex with value −20, −15, −10, −5, 5, 10, 15, 20 |
| `Z` | reserved, must not occur |

Balls are **not** in the grid (section 3.6); a cell with a ball and no feature is plain floor.

**End of the grid / digits.** A floor run never exceeds the number of remaining cells R. While reading digits, stop as soon as the value read equals R: that run is the last token of the grid and any further digits belong to the next section. (This is unambiguous: a proper prefix of a digit string is always smaller than the whole string.) The encoder writes the trailing floor run explicitly.

**Wall runs.** A run of n ≥ 1 consecutive plain wall cells is written greedily: `f` repeated ⌊n/6⌋ times, then the letter for the remainder (if any). A wall cell with a gap letter (`g`–`j`) is not a plain wall and ends the run.

### 3.3 Edge openings

One character `N62[k]` = number of tunnel openings on the board edge, then `k` characters, each the **perimeter index** of one opening, in ascending order. The perimeter has `2(w+h)` segments (at most 60), counted counter-clockwise from the bottom-left:

- bottom edge, cell `(x, 1)`, side `d`: index `x-1`
- right edge, cell `(w, y)`, side `r`: index `w + (y-1)`
- top edge, cell `(x, h)`, side `u`: index `w + h + (w-x)`
- left edge, cell `(1, y)`, side `l`: index `2w + h + (h-y)`

The opening's floor cell may hold any feature (goal, teleport, arrow, …; level 16.9 has a teleport with an edge opening), and a corner cell can have two edge openings (two indices). The floor cell itself is never a wall (RULES.md §2).

### 3.4 Tunnel pairing

Let the **opening list** O be: the wall-gap openings in grid (cell) order, followed by the edge openings in perimeter order. Its length is `2P` (P = number of tunnel pairs; must be even). Pairing is stored as P−1 characters: repeatedly take the lowest unpaired opening and pair it with the j-th (0-based) of the *other* unpaired openings in order, writing `N62[j]`; the last pair is forced and writes nothing. In the decoded board a pair is `{a, b}` with `a` the lower opening of O. (Pairing cannot be derived: only 3 of 105 catalog pairs are straight wraps.)

### 3.5 Switch mapping

Absent if the board has no switches. Otherwise:

- `N62[g]`, the number of switch groups (switches with identical control lists form one group; groups are numbered 1… in the order of their first switch, so numbering is canonical).
- If `g == 1`: every switch and every gate belongs to group 1 and nothing more is written for them. If `g ≥ 2`: one character per **switch** in cell order, then one per **gate** in cell order, each the group number.
- One character per **teleport** in cell order (always written when switches exist): group number, or 0 = not switchable. An inactive teleport must be non-zero.

IDs are not stored: gates `G1…`, teleports `T1…`, switches `S1…` follow cell order, and a switch's `controls` list is rebuilt from the groups. The switch indicator (`on`) is display state (RULES.md §3) and is not stored; it is derived by `Core.validateBoard` for every input format: a switch is on exactly when every gate and teleport it controls starts active, otherwise off. Check how hexes are named today (K3 stores hex ids explicitly, e.g. `hex1`, `hex2` in level 1.7) and regenerate them by cell order; ids are labels only, so renaming existing ids is acceptable.

### 3.6 Balls

`N62[b]` = number of balls (1–61), then `b` entries of two N62 characters, each the value `v = 4 * cellIndex + colourIndex` (colour R=0, G=1, B=2, Y=3; `v` ≤ 899, written as `N62[⌊v/62⌋] N62[v mod 62]`), in ascending `v`. Ball ids (`R`, `R1`, …) are not stored; they come from `Core.validateBoard` (RULES.md §4) regardless of storage order. A ball may share a cell with a floor feature as before.

## 4. Canonical form and decoding

- The encoder produces exactly one string per valid board: maximal floor runs, greedy wall runs, ascending lists, canonical group numbering, no reserved symbols, no trailing characters. **The solver emits the same canonical K4** (`solver.cpp` implements it independently, as it does K3).
- The decoder is strict like K3's (which rejects non-canonical base64): after decoding it **re-encodes and requires equality** with the input, then runs `Core.validateBoard`.
- Errors: unknown symbol, `Z`, a grid that overruns or underruns `w*h`, leading-zero run, odd opening count, out-of-range index or group, trailing characters.

## 5. What K4 does not store (decisions to confirm in the implementation conversation)

K3 stores `id`, `title`, an optional `description` and the **solution** inside the code. *(Catalog check: all 300 titles are exactly `Level <id>`, no level has a description, all 300 carry an embedded solution of at most 205 characters in text notation.)* Recommended:

- **K4 is the board only**: no id, title, description or solution. The catalog line supplies the id and the title is derived (`Level <id>`); the editor's custom title/description are not part of the code.
- **Catalog line format:** `1.1 = K4.<code>` followed by the solution in the text notation of RULES.md §5 (whitespace separated, human readable, diffable). Pick the exact separator when implementing; update `catalog.js` and the tools that read `levels.js` (solver `--catalog`, statistics scripts, `Solver/tests`).
- **Share links / replay links** keep carrying board code and moves as separate parameters (check `readShareUrl` / `makeShareUrl`); old K3 links stop working, which is accepted.

## 6. Implementation plan (suggested order)

1. **JS codec (`codec.js`)**: add K4 encode/decode next to K3 and a round-trip test on **all 300 real levels** (decode K3 → encode K4 → decode → boards equal ignoring id/title/solution; solutions replayed through `engine.js`). Per the project's testing preference: no random board suites; a handful of hand-made edge fixtures only (level 16.9 covers an edge opening plus wall gaps plus a double-opening floor cell; add a 15×15 board and a corner cell with two edge openings).
2. **Validation and editor**: tighten `Core.validateBoard` and `editor.js` (hex selector with the 8 values, 15×15 limit, one opening per wall cell, switch list rules, ball limit) and RULES.md §6.
3. **One-time migration** of `levels.js` with a tool in `tools/` (like `migrate-teleports.js`). Afterwards replay every embedded solution and confirm it completes the board (DATA-001: never overwrite `levels.js` with a starter file; keep a backup until verified).
4. **Native solver** (`Solver/solver.cpp`): replace the K3 parser and emitter (`parseCode`, the `--json` code field, `--no-code`, README) by K4, bump `SOLVER_VERSION`, rebuild the Linux binary (`make release`) and the WASM bundle (`node wasm/build.js`). Update `Solver/tests` (`verify.js`, `mechanics.js`, the random tests) that build K3 codes.
5. **Remove K3**: `codec.js` K3 reader/writer, `parser/encode_k3.*`, the "Unsupported board-code version; this player supports K3" message (now K4), share-link handling, all K3 references in the docs (ARCHITECTURE.md §4 "K3 binary board format" is replaced by a pointer to this file or by this content). The editor's export and the Import dialog use K4.
6. **Docs and version**: bump `APP_VERSION` in `app.js` (check upstream for the current value first), move this specification into ARCHITECTURE.md or keep it here (update the link in STATUS.md), and delete "not implemented" status text when done.

Add two or three worked examples (e.g. level 1.1 and level 16.9) to this file after the first implementation, as regression anchors.

## 7. Implementation notes (2026-11-24)

- `codec.js`: `Codec.encodeBoard(board)` writes K4 and `Codec.decodeBoard` reads it (strict: re-encodes and compares; semantic problems go to the optional `problems` array). `Core.validateBoard` enforces the section 2 limits; the editor offers the eight hexagon values and sizes up to 15. Share links carry the K4 board code and the route as separate parameters. `solver.cpp` has its own `codeK4`/`parseCode` (outputs `K4:` and JSON `k4`).
- **Catalog line (superseded by 4.5.0, see below):** `1.1 = K4.<board code> <solution>`. `app.js` builds each level as the decoded board plus `id`, title `Level <id>` and the solution. Decoded ids: gates `G1…`, switches `S1…`, teleports `T1…`, hexagons `hex1…`, all in cell order.
- The one-time `levels.js` migration (done in 3.20.0, tool since removed): all 300 levels round-tripped K3 → K4 with equal boards and identical solution replays. K4 payloads (incl. balls) average 47.0 characters (12–116). **Switch indicator `on` is not stored**: level 18.8 had it on and now starts off (replay unaffected).
- `tools/test-k4.js`: catalog check plus fixtures and rejection cases.

### Worked examples (regression anchors)

- Level 1.1: `K4.3401pa6a2010F`, solution `Gd`. Header `3` `4` `0` (3 wide, 4 high, blue); grid `1` floor, `p` goal G, `a` one wall, `6` floor, `a` one wall, `2` floor (12 cells); `0` edge openings (so no pairing); no switches; `1` ball, `0F` = 41 = 4·10 + 1 → cell 10 (x 2, y 4), green.
- Level 16.9 (edge opening, wall gaps, double-opening floor cell, teleports, switch): `K4.a821zb2jb3av1dqf1bs3ja2ja2eDb1bhfs3ahaDjao1agazv1bu7049msvyc68541100000020E0K`, solution `RlulddrudBddru`.
- **Embedded route (4.5.0):** a K4 code may be followed directly (no separator) by an alphanumeric **compact route**: `K4.<board><route>`. The board is self-delimiting, so whatever follows the balls is the route. The route is the compact binary route of `codec.js` (varint move count, choice mode, packed ball/direction indices; since 4.8.0 the ball index is the ball's rank among the unlocked balls in the position before the move, RULES.md §4) behind a leading sentinel 1, read as one number and written in base 62 (`N62` digits; canonical, leading zeros rejected). On the 300 catalog solutions it is 4,925 characters against 8,746 for the comma-free text notation. This is the **only** route encoding: levels.js lines are `id = K4.<board><route>`, Export ("Include route") emits it, Import and permalinks (`#board=K4.<board><route>&at=n`) accept it. The earlier forms (a separate `route=`/`moves=` parameter, base64url, `K4.<code> <text route>` with a space, and a `Z` separator tried in 4.4.0) were removed. The solver ignores a route after the board code. `tools/test-k4.js` round-trips all 300 catalog routes.
- **Solution text notation** (RULES.md §5, the readable form in the Replay panel, solver output and `parseSolution`) has no commas: groups are written back to back; commas and spaces are still ignored on input.
